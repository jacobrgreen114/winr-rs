# winr

A small Windows windowing library for Rust 1.92+. This branch redesigns the early
callback API around a thread-affine event loop. Other native backends are out of scope.

```no_run
# #[cfg(windows)]
# fn main() -> winr::WinrResult<()> {
use winr::application::{Event, EventLoop};
use winr::window::{WindowBuilder, WindowEvent};
use winr::Extent;

EventLoop::new()?.run(|event_loop, event| -> winr::WinrResult<()> {
    match event {
        Event::Started => {
            let window = WindowBuilder::new()
                .with_title("Hello")
                .with_extent(Extent::new(800, 600))
                .build(event_loop)?;
            window.show()?;
        }
        Event::Window { id, event: WindowEvent::CloseRequested } => {
            if let Some(window) = event_loop.window(id) { window.close()?; }
        }
        Event::Window { event: WindowEvent::Closed, .. } => event_loop.exit(),
        _ => {}
    }
    Ok(())
})
# }
# #[cfg(not(windows))]
# fn main() {}
```

The loop owns native windows. Dropping or cloning a `Window` handle does not change
native lifetime. Close explicitly, or let the loop destroy its windows on exit.
Handles can outlive the loop; operations on them return `WindowClosed`. Both loop
and handles are `!Send` and `!Sync`. Only one loop may exist per thread.

Application state belongs in the handler's captured variables or in a struct with
an event-handling method. `run` is generic over the handler and its error type;
there is no trait object dispatch in the event path. Errors must implement
`From<WinrError>` and return directly from `run`. An application panic unwinds
through Rust code, with loop cleanup, rather than through a Win32 procedure.

## Dispatch and lifetime

The native procedure updates `Cell` state or appends an owned event to a reusable
queue. It never invokes application callbacks. The loop dispatches a bounded batch
of native messages, then queued events, then `AboutToWait`. Events generated by a
handler are delivered on the next iteration. No queue borrow crosses a callback or
a Win32 call. Creation-time messages are handled internally; `Created` is the first
public event for a successfully created window.

`CloseRequested` is a notification: call `close()` to accept it or do nothing to
veto it. `Closed` is emitted once, after native destruction finishes. Default
system-key processing is preserved, including Alt+F4. `LoopExiting` is delivered
on normal exit; final native cleanup follows it. Events generated during final
cleanup are discarded. Error and panic exits also clean up, without `LoopExiting`.
The loop does not automatically exit when the last window closes.

The default control flow is `Wait`, which sleeps until input arrives.
Use `Poll` for continuous rendering, or `WaitUntil(Instant)` for timers/animation.
An expired deadline stays expired until the handler updates it. Pending input is
included in waits, even if a nested native call previously inspected the queue.

Native state has a stable `Rc` allocation. Userdata owns a strong reference from
`WM_NCCREATE` through `WM_NCDESTROY`; each procedure invocation temporarily owns
another, so nested destruction cannot invalidate an active procedure. Userdata is
detached before final default processing. All state mutation uses scoped interior
mutability; the procedure never reconstructs an exclusive window reference.
The library denies implicit unsafe operations in unsafe functions. Internal native
procedure panics are contained when unwinding is enabled and reported as errors.
If native destruction fails during best-effort cleanup, its userdata reference is
retained rather than leaving a dangling pointer.

## Geometry and input

- Creation extents, size setters, and min/max constraints describe the **outer**
  window rectangle in physical pixels. Resize events report the **client** area.
- Set-position uses the outer screen position; moved events report the client
  origin in screen coordinates. Negative positions are supported.
- Pointer event positions consistently use client coordinates. Wheel deltas use
  native units (120 per conventional detent).
- Invalid sizes, contradictory constraints, and embedded title NULs return errors.
- Key codes use checked mappings and preserve unsupported codes as `Unknown(u32)`.
  Right Shift uses its scan code; right Control/Alt and numpad Enter use the extended bit.
- Character messages decode UTF-16 surrogate pairs. Malformed sequences produce
  replacement characters. Physical key events and character events are separate.

The host application controls process DPI awareness. Automatic DPI scaling, IME
composition, mouse capture, and raw input are not implemented in this branch.
Native handles are borrowed escape hatches: replacing userdata/window procedures
or destroying the window externally violates the library's ownership contract.

## Migration from the original API

`ApplicationCallbacks`, `WindowCallbacks`, `WindowPtr`, and the platform trait
hierarchy have been removed. Replace `application().with_callbacks(...).run()` with
`EventLoop::new()?.run(handler)`, and `window().with_style(...)` with
`WindowBuilder::new()` and its geometry/decoration options. Keep per-window user
state in the handler, keyed by `WindowId`. IDs are scoped to their event loop.
`Window` methods use shared references and no longer dereference to callback state.
This is an intentional breaking redesign, not a compatibility layer.

## Development

On Windows with the MSVC Rust toolchain and Windows SDK:

```text
cargo test --all-targets
cargo test --doc
cargo clippy --all-targets -- -D warnings
cargo run --example normal_window
```

The Windows workflow runs native lifecycle, deferred dispatch, error/panic cleanup,
input, and timer tests. On Linux, `cargo test --lib` exercises portable decoding and
geometry helpers; it does not validate native window behavior. Cross-check Windows
code with `cargo check --all-targets --target x86_64-pc-windows-msvc` after installing
that Rust target. Host compilation exposes only input and geometry types; it does
not provide another window backend.
